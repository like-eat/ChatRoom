# Gin 学习第四阶段：生产级实践 —— 一个"发消息"接口打通全部防线

> 场景：`POST /api/msg/send` 发消息，假设这是**线上微信**。
> 一条接口里实现：**参数校验、幂等、限流、熔断、降级、重试、高并发**。
> 新建一个文件夹，把下面 7 个 .go 文件复制进去，`go run .` 就能跑。
> **Redis 可不启动**——Redis 挂了会自动走降级路径（这本身就是演示的一部分）。

---

## 项目结构

```text
prod-demo/
├── main.go        # 路由 + 发消息接口（串起全部防线）+ 并发演示
├── dto.go         # 请求DTO + 参数校验（binding tag）
├── limiter.go     # 限流：每用户令牌桶
├── dedup.go       # 幂等：Redis SETNX 去重（带降级）
├── breaker.go     # 熔断：保护下游
├── retry.go       # 重试：指数退避
└── downstream.go  # 模拟下游（Kafka/推送）+ 降级队列
```

## 一张图看全链路

```
用户点"发送"
  ↓  POST /api/msg/send {session_id, client_msg_id, type, content, ...}
  ↓
① 参数校验  ShouldBindJSON + binding tag
   └─ 非法参数 → 400 "参数错误"
  ↓
② 限流      每用户令牌桶（20条/秒，突发50）
   └─ 超限 → 429 "发送太频繁"
  ↓
③ 幂等      Redis SETNX(client_msg_id)
   ├─ Redis挂了 → 降级为内存去重 → 记日志继续（可能重复但不丢消息）
   └─ 重复请求 → 200 "重复消息已忽略"
  ↓
④ 熔断 + 重试  保护下游(Kafka/推送)：指数退避重试3次
   ├─ 熔断开启 → 降级：进兜底队列，200 "已排队稍后送达"
   ├─ 重试3次仍失败 → 500 "发送失败"
   └─ 成功 → 200 "发送成功"
```

**每一条防线挡住一个问题，防线之间互相独立又层层递进。**

## 1. dto.go — 参数校验（声明式）

```go
package main

// SendMsgReq 发消息请求。
// binding tag = 声明式校验：Gin 在"绑定"阶段就按规则拦截非法参数，
// 进不到业务代码。这就是"参数校验"的正确姿势。
type SendMsgReq struct {
	SessionId   string `json:"session_id"    binding:"required,len=20"`                 // 会话UUID（S开头20位）
	ClientMsgId string `json:"client_msg_id" binding:"required,max=64"`                 // 客户端生成的幂等键（重试时必须保持不变！）
	Type        int8   `json:"type"          binding:"required,oneof=0 1 2"`            // 0文本 1语音 2文件
	Content     string `json:"content"       binding:"required_if=Type 0,max=2000"`     // 文本消息内容（Type=0 时必填）
	Url         string `json:"url"           binding:"required_if=Type 2"`              // 文件消息URL（Type=2 时必填）
	SendId      string `json:"send_id"       binding:"required,max=20"`                 // 发送者UUID
	ReceiveId   string `json:"receive_id"    binding:"required,max=20"`                 // 接收者UUID
}
```

**为什么这样设计：**
- `required`：必填，空值直接 400
- `len=20`：会话ID必须正好20位（匹配项目的 char(20)）
- `oneof=0 1 2`：消息类型只能三选一，传 5 直接拦截
- `required_if=Type 0`：类型是文本时，content 必填——**条件式校验**，比全部必填更贴近真实业务
- 校验失败 → `ShouldBindJSON` 返回 err → 接口 400，**非法请求根本到不了业务层**

## 2. limiter.go — 限流（每用户令牌桶）

```go
package main

import (
	"sync"

	"golang.org/x/time/rate"
)

// UserLimiter 每用户令牌桶限流器。
// 令牌桶原理：每秒往桶里放 r 个令牌，桶最多装 b 个。
//   每次请求取 1 个令牌，取得到=放行，取不到=拒绝。
// 类比：微信用户每秒最多发 20 条消息，但允许突发连续点 50 条。
type UserLimiter struct {
	mu    sync.Mutex
	users map[string]*rate.Limiter // userID → 他自己的桶
	r     rate.Limit               // 每秒补充多少令牌
	b     int                      // 桶容量（突发上限）
}

func NewUserLimiter(r rate.Limit, b int) *UserLimiter {
	return &UserLimiter{users: make(map[string]*rate.Limiter), r: r, b: b}
}

// Allow 判断某个用户这次请求是否放行
func (ul *UserLimiter) Allow(userID string) bool {
	ul.mu.Lock()
	defer ul.mu.Unlock()

	l, ok := ul.users[userID]
	if !ok { // 该用户第一次请求，给他建个桶
		l = rate.NewLimiter(ul.r, ul.b)
		ul.users[userID] = l
	}
	return l.Allow()
}
```

**为什么按"每用户"而不是"全局"：**
- 全局限流：一个用户刷屏会把所有人的消息都堵住（**误伤**）
- 每用户限流：各管各的，张三刷屏只限张三（**隔离**）

`sync.Mutex` 保护 map（并发建桶安全）——你学过的并发知识点在这用上了。

## 3. dedup.go — 幂等（Redis SETNX + 降级）

```go
package main

import (
	"context"
	"sync"
	"time"

	"github.com/go-redis/redis/v8"
)

// Dedup 幂等去重器。
// 微信场景：用户网络抖动，客户端会重试发送。同一个 client_msg_id 只允许处理一次。
// 核心：Redis SETNX —— 键不存在才设置成功：
//   成功 = 第一次处理
//   失败 = 键已存在 = 重复请求，直接丢弃
// 降级：Redis 挂了 → 退化成单机内存去重（同节点有效，跨节点可能重复，可接受）。
type Dedup struct {
	rdb *redis.Client
	mem sync.Map      // 内存降级用
	ttl time.Duration // 幂等键保留多久（过期后同一msg_id可再次发送）
}

func NewDedup(rdb *redis.Client, ttl time.Duration) *Dedup {
	return &Dedup{rdb: rdb, ttl: ttl}
}

// Mark 标记某个幂等键已处理。返回 (是否重复, 错误)。
// 错误时表示降级（Redis不可用），上层记日志后继续，不丢消息。
func (d *Dedup) Mark(userID, msgID string) (bool, error) {
	key := "dedup:msg:" + userID + ":" + msgID
	if d.rdb != nil {
		ok, err := d.rdb.SetNX(context.Background(), key, "1", d.ttl).Result()
		if err == nil {
			return !ok, nil // ok=true首次；ok=false重复
		}
		// Redis 不可用：降级到内存去重，并上报降级信号
		return d.markMem(key)
	}
	return d.markMem(key)
}

// markMem 内存降级版（简化：不做真正的过期清理，演示用）
func (d *Dedup) markMem(key string) (bool, error) {
	_, loaded := d.mem.LoadOrStore(key, time.Now())
	if loaded {
		return true, ErrDegraded // 已存在=重复
	}
	return false, ErrDegraded
}
```

**为什么是 SETNX 而不是"先查再写"？** 因为"查→写"两步之间可能有并发（两个请求同时查到都不存在，都去处理）——**不是原子的**。`SETNX` 一条命令搞定"不存在才设置"，原子，天然防并发。这就是数据库里**唯一索引**在 Redis 里的对应物。

> 真实项目里，MySQL 的 `message.uuid` 还应该有唯一索引兜底（即使 Redis 也漏了，数据库唯一约束再挡一道）。**幂等要双层保险。**

## 4. breaker.go — 熔断器

```go
package main

import (
	"errors"
	"sync"
	"time"
)

var ErrCircuitOpen = errors.New("熔断已开启")

// CircuitBreaker 熔断器，保护下游（Kafka/推送通道）。
// 三个状态：
//   CLOSED(0)   关闭：正常放行；连续失败 threshold 次 → 打开
//   OPEN(1)     打开：直接拒绝，不再打下游；openTimeout 后 → 半开
//   HALF_OPEN(2) 半开：放一个探路请求，成功→关闭，失败→重新打开
type CircuitBreaker struct {
	mu          sync.Mutex
	state       int // 0关闭 1打开 2半开
	failures    int // 当前连续失败次数
	threshold   int // 连续失败多少次触发熔断
	openUntil   time.Time
	openTimeout time.Duration
}

func NewCircuitBreaker(threshold int, openTimeout time.Duration) *CircuitBreaker {
	return &CircuitBreaker{threshold: threshold, openTimeout: openTimeout}
}

// Call 包一层执行：熔断开着就直接拒绝，不浪费下游资源
func (cb *CircuitBreaker) Call(fn func() error) error {
	cb.mu.Lock()
	switch cb.state {
	case 1: // OPEN
		if time.Now().After(cb.openUntil) {
			cb.state = 2 // 熔断到期 → 转半开，放一个探路请求
		} else {
			cb.mu.Unlock()
			return ErrCircuitOpen // 熔断中，快速失败
		}
	case 2: // HALF_OPEN 半开：放行这个探路请求（简化版未做并发名额限制）
	}
	cb.mu.Unlock()

	if err := fn(); err != nil {
		cb.mu.Lock()
		cb.failures++
		if cb.failures >= cb.threshold {
			cb.state = 1
			cb.openUntil = time.Now().Add(cb.openTimeout)
		}
		cb.mu.Unlock()
		return err
	}
	cb.mu.Lock()
	cb.failures = 0
	cb.state = 0 // 成功 → 关闭
	cb.mu.Unlock()
	return nil
}
```

**为什么要熔断？** 下游（Kafka/推送）挂了，如果每次请求都去打它，下游被压得更死（**雪崩**）。熔断 = **主动刹车**：连续失败 N 次，后面直接拒之门外，让下游喘息恢复。

## 5. retry.go — 指数退避重试

```go
package main

import (
	"errors"
	"time"
)

// Retry 指数退避重试。
//   attempts  最多试几次
//   baseDelay 初始间隔，每次翻倍：100ms, 200ms, 400ms...
// 只重试"可重试"的错误（网络抖动、下游暂时过载）；
// 业务错误（如消息格式被拒）立即返回，不浪费重试。
func Retry(attempts int, baseDelay time.Duration, fn func() error) error {
	var err error
	for i := 0; i < attempts; i++ {
		if err = fn(); err == nil {
			return nil
		}
		if !IsRetryable(err) {
			return err
		}
		time.Sleep(baseDelay * time.Duration(1<<i)) // 100ms → 200ms → 400ms
	}
	return err
}

// IsRetryable 判断错误是否值得重试
func IsRetryable(err error) bool {
	return errors.Is(err, errDownstreamDown) // 只有"下游暂时不可用"才重试
}
```

**为什么指数退避而不是"固定等1秒重试3次"？**
- 固定间隔：下游刚好过载，你每秒打一次，等于**持续骚扰**
- 指数退避：100→200→400ms，越等越久，给下游恢复时间
- 还要注意：**不是所有错误都值得重试**——消息格式错，重试一万次也是错，纯浪费

## 6. downstream.go — 模拟下游 + 降级

```go
package main

import (
	"errors"
	"fmt"
	"sync/atomic"
	"time"
)

var (
	// 模拟下游（Kafka Producer / 实时推送通道）的可用性开关
	downstreamDown int32 // 1=故障中

	errDownstreamDown = errors.New("下游暂时不可用") // 可重试
	errBadMessage     = errors.New("消息格式被下游拒绝") // 不可重试
)

// ErrDegraded 降级信号（任何依赖退化时上报）
var ErrDegraded = errors.New("依赖降级")

// sendToDownstream 模拟"把消息推给实时通道/Kafka"。
// 真实场景这里是：
//   kafka.WriteMessages(ctx, ...)  或  chatServer.Send(msg)
// 这里用开关模拟故障，用来演示熔断+重试。
func sendToDownstream(req SendMsgReq) error {
	if atomic.LoadInt32(&downstreamDown) == 1 {
		return errDownstreamDown // 可重试：网络抖动/下游过载
	}
	if req.Content == "" && req.Url == "" {
		return errBadMessage // 不可重试：消息本身有问题
	}
	time.Sleep(5 * time.Millisecond) // 模拟真实耗时
	return nil
}

// fallbackQueue 降级：熔断/失败期间，消息进本地兜底队列，稍后补偿。
// 真实场景：写入延迟队列 / 定时补偿任务 / 人工介入，保证"消息不丢"。
func fallbackQueue(req SendMsgReq) {
	fmt.Printf("  [降级] 消息 %s 已进兜底队列，稍后补偿发送\n", req.ClientMsgId)
}

// setDownstreamDown 控制下游故障开关（演示用）
func setDownstreamDown(v bool) {
	if v {
		atomic.StoreInt32(&downstreamDown, 1)
	} else {
		atomic.StoreInt32(&downstreamDown, 0)
	}
}

// degradeNote 降级日志（真实场景用 zlog.Warn）
func degradeNote(component string, err error) {
	fmt.Printf("  [降级] %s 不可用(%v)，走降级路径，不影响主流程\n", component, err)
}
```

**降级的核心思想：** 主链路里有个依赖挂了，**不要跟着一起挂**——退而求其次（内存去重、兜底队列），保证"消息不丢、用户无感"，等依赖恢复再补偿。

## 7. main.go — 组装一切 + 并发演示

```go
package main

import (
	"errors"
	"fmt"
	"net/http"
	"sync"
	"time"

	"github.com/gin-gonic/gin"
	"github.com/go-redis/redis/v8"
	"golang.org/x/time/rate"
)

// ===== 全局依赖（真实项目从配置文件/容器注入）=====
var (
	// 连 Redis。DialTimeout 调小，让"Redis挂了"能快速降级，而不是傻等5秒
	rdb = redis.NewClient(&redis.Options{
		Addr:        "localhost:6379",
		Password:    "",
		DB:          0,
		DialTimeout: 500 * time.Millisecond,
	})

	// 每用户每秒 20 条，突发 50 条
	userLimiter = NewUserLimiter(rate.Limit(20), 50)

	// 幂等键保留 24 小时（真实微信通常按业务定：几分钟到几天）
	dedup = NewDedup(rdb, 24*time.Hour)

	// 下游熔断：连续失败 3 次，熔断 5 秒
	downstreamBreaker = NewCircuitBreaker(3, 5*time.Second)
)

// SendMsg 发消息接口 —— 一条接口串起全部防线
func SendMsg(c *gin.Context) {
	var req SendMsgReq

	// ① 参数校验：binding tag 在绑定阶段拦截非法参数
	if err := c.ShouldBindJSON(&req); err != nil {
		JsonBack(c, 400, "参数错误: "+err.Error(), nil)
		return
	}

	// ② 限流：每用户令牌桶，防刷屏/防风暴
	if !userLimiter.Allow(req.SendId) {
		JsonBack(c, 429, "发送太频繁，请稍后再试", nil)
		return
	}

	// ③ 幂等：同一 client_msg_id 只处理一次（客户端重试/网络重发都拦住）
	duplicated, err := dedup.Mark(req.SendId, req.ClientMsgId)
	if err != nil { // Redis 挂了 → 降级（内存去重），记日志继续
		degradeNote("Redis幂等", err)
	} else if duplicated {
		JsonBack(c, 200, "重复消息，已忽略（幂等生效）", gin.H{"msg_id": req.ClientMsgId})
		return
	}

	// ④ 熔断 + 重试：保护下游（Kafka/推送）。熔断期内直接走降级
	err = downstreamBreaker.Call(func() error {
		return Retry(3, 100*time.Millisecond, func() error {
			return sendToDownstream(req)
		})
	})
	if err != nil {
		if errors.Is(err, ErrCircuitOpen) {
			// ⑤ 降级：熔断期间改走兜底队列，不阻塞用户
			fallbackQueue(req)
			JsonBack(c, 200, "服务繁忙，消息已进队列，稍后送达", gin.H{"msg_id": req.ClientMsgId})
		} else {
			JsonBack(c, 500, "发送失败: "+err.Error(), nil)
		}
		return
	}

	JsonBack(c, 200, "发送成功", gin.H{"msg_id": req.ClientMsgId})
}

// handleSend 核心处理逻辑（与 HTTP 解耦，方便并发演示直接调用）
func handleSend(req SendMsgReq) (int, string, gin.H) {
	// ① 校验（演示里已经传了合法结构体，这里简化）
	// ② 限流
	if !userLimiter.Allow(req.SendId) {
		return 429, "发送太频繁，请稍后再试", nil
	}
	// ③ 幂等
	duplicated, err := dedup.Mark(req.SendId, req.ClientMsgId)
	if err != nil {
		degradeNote("Redis幂等", err)
	} else if duplicated {
		return 200, "重复消息，已忽略（幂等生效）", gin.H{"msg_id": req.ClientMsgId}
	}
	// ④ 熔断+重试
	err = downstreamBreaker.Call(func() error {
		return Retry(3, 100*time.Millisecond, func() error { return sendToDownstream(req) })
	})
	if err != nil {
		if errors.Is(err, ErrCircuitOpen) {
			fallbackQueue(req)
			return 200, "服务繁忙，消息已进队列，稍后送达", gin.H{"msg_id": req.ClientMsgId}
		}
		return 500, "发送失败: " + err.Error(), nil
	}
	return 200, "发送成功", gin.H{"msg_id": req.ClientMsgId}
}

// JsonBack 统一返回格式
func JsonBack(c *gin.Context, code int, msg string, data interface{}) {
	body := gin.H{"code": code, "message": msg}
	if data != nil {
		body["data"] = data
	}
	c.JSON(http.StatusOK, body) // HTTP永远200，业务状态在body.code（和项目一致）
}

// demoConcurrent 高并发 + 幂等 + 熔断演示（服务启动后自动跑一遍）
func demoConcurrent() {
	time.Sleep(500 * time.Millisecond)
	fmt.Println("\n========== ① 高并发 + 幂等演示 ==========")
	// 50 个并发请求，其中前 10 个用同一个 client_msg_id（模拟客户端重试）
	var wg sync.WaitGroup
	start := time.Now()
	for i := 0; i < 50; i++ {
		wg.Add(1)
		go func(i int) {
			defer wg.Done()
			msgID := fmt.Sprintf("msg-%d", i)
			if i < 10 {
				msgID = "msg-retry-same" // 前10个重复发送同一个幂等键
			}
			req := SendMsgReq{
				SessionId: "S12345678901234567890", ClientMsgId: msgID,
				Type: 0, Content: "你好", SendId: "U1", ReceiveId: "U2",
			}
			code, msg, _ := handleSend(req)
			fmt.Printf("  并发[%02d] msg_id=%-14s → code=%d %s\n", i, msgID, code, msg)
		}(i)
	}
	wg.Wait()
	fmt.Printf("  50 个并发请求完成，总耗时 %v\n", time.Since(start))

	fmt.Println("\n========== ② 熔断演示：把下游打挂 ==========")
	setDownstreamDown(true) // 模拟 Kafka/推送挂了
	for i := 0; i < 10; i++ {
		req := SendMsgReq{
			SessionId: "S12345678901234567890", ClientMsgId: fmt.Sprintf("breaker-%d", i),
			Type: 0, Content: "测试", SendId: "U1", ReceiveId: "U2",
		}
		code, msg, _ := handleSend(req)
		fmt.Printf("  熔断[%02d] → code=%d %s\n", i, code, msg)
	}
	setDownstreamDown(false)
	fmt.Println("  下游已恢复（半开探路成功后熔断器自动关闭）")
}

func main() {
	go demoConcurrent() // 先跑演示，同时把服务开起来

	r := gin.Default()
	r.POST("/api/msg/send", SendMsg)

	fmt.Println("🚀 服务启动: http://127.0.0.1:8080")
	fmt.Println("测试: curl -X POST -H 'Content-Type: application/json' \\")
```

## 每个防线怎么验证

| 防线 | 怎么触发 | 期望看到 |
|---|---|---|
| **参数校验** | `curl` 去掉 `content` 字段发文本消息 | `{"code":400,"message":"参数错误: ..."}` |
| **限流** | 把 `b` 改成 5，连续快速发 10 条 | 前 5 条成功，后面 `code=429 发送太频繁` |
| **幂等** | 启动后看控制台 ① 部分 | 前 10 个同 msg_id：第 1 个"发送成功"，其余 9 个"重复消息已忽略" |
| **熔断** | 看控制台 ② 部分（下游被打挂） | 前 3 条重试后 500，第 4 条起直接"已进兜底队列"（熔断开了）|
| **降级** | 不启动 Redis 跑一次 | 控制台打 `[降级] Redis幂等 不可用(...)`，但消息照常发送成功 |
| **重试** | 看 ② 部分的耗时（每条约 700ms=100+200+400ms 三次退避）| 每条失败消息都在"指数退避"后才放弃 |

## 对照真实微信（面试能说的深度）

这套 mock 就是微信消息链路的最小骨架。真实微信在此基础上还有：
- **参数校验**：反垃圾、敏感词、超长内容截断
- **幂等**：`client_msg_id` + MySQL `message.uuid` 唯一索引**双层保险**，重试不重发
- **限流**：除了人均，还有**全局水位**（每秒总消息数封顶）、风控降级（异常账号直接停发）
- **熔断/降级**：推送通道（长连接）熔断时，消息改走**离线存储**，用户上线补推
- **重试**：延迟队列 + 定时补偿，失败消息几分钟内自动重发

**一句话：一个"能跑"的接口和"能扛"的接口，差的就是这 7 个文件的防线。你把这个接口跑通、看明白每条防线，面试讲"高可用设计"就有真东西可讲了。**
